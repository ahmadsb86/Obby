Main problem: Its easier and faster to compile a program file-by-file. But if these are parallelized how do you do interprocedular optimizations if information cannot be passed between files? A function call defined in another file cannot be inlined (and a lot of other interprocedual optimizations).

3 main routes to compilation (from slowest to fastest):

1. To ensure your whole library file just gets stitched into main file and library definitions visible at compile time, you use header-only file (header file contains declarations AND definitions). non header-only has only declarations (and thats all compiler sees at compile time of main file)

2. LTO is when we compile files seperately but only to intermediate level (.o files) and then at link time we are able to optimize somewhat. 

3. Dynamic linking. Libs are machine code shared by multiple processes. Absolutely no interprocedural optimization.

4 O-levels (flags for optimization levels) on gcc. -march informs abt target processor (for more processor-specific optimizations). -mtune for tuning (optimizing but doesn't introduce instructions incompatible with other processors)

You can use attribute-based syntax to select between multiversioned functions (seperate implementations tailored to diff processors) automatically during compile time:

-funroll-loops will unroll loops globally if before entering loop (or at compile time) we know the number of iterations.

function inlining is best for compiler to decide

POGO (profile on test data, used to inform optimizations e.g. likeliness of branch)

```
g++ -fprofile-generate [other flags] source.cc -o binary
```

generates .gcda profile logs that can be used to rebuild with

```
g++ -fprofile-use [other flags] source.cc -o binary
```

maybe 10-20% improvement for large codebases

C++ has intentionally undefined behavior (compiler allowed to do anything) because
1. Div by zero or null ptr ref are likely bugs and UB easier to catch than e.g. returning 0
2. Sometimes instructions do diff things on diff processors and it costs to add a check of processor to keep instruction well-defined. Usually designated implementation-defined rather than undefined unless point 3
3. Things like keeping signed int overflow as undefined even though for virtually all processors `INT_MAX + 1 == INT_MIN` allows compiler to optimize using the fact that necessarily $x>y \implies x+1>y$ 

You can use assume to give compiler info on things like if a number will always be positive (allows div by two to be optimized to just one right shift)
