statistical profiling: lets you go down to the assembly level and track various _hardware events_ such as branch mispredictions or cache misses, which are critical for performance.

cpus have counters that listen to events such as branch mispredicts, cache miss etc. configurable by software. only 8-16 counters so the program must be intermittently stopped, counter reconfigured for another event, and resumed (multiplexing) to get statistical estimates for stats on many diff events (`perf stat`)

To see which parts of program are bottlenecking, we can stop/rerun program many times,  inspecting instruction pointer's location (`perf record`), but because of pipelining/OOO execution, "current" can be vague. solved with

[Program simulation](https://en.algorithmica.org/hpc/profiling/mca): Cachegrind only tracks memory accesses and branches and does so by replacing those interesting instructions in assembly with software data structures that simulate branches and caches. 

A _machine code analyzer_ is a program that takes a small snippet of assembly code and [simulates](https://en.algorithmica.org/hpc/profiling/simulation) its execution on a particular microarchitecture using information available to compilers, and outputs the latency and throughput of the whole block, as well as cycle-perfect utilization of various resources within the CPU.

`llvm-mca` simulates whole cpu and can tell you things like which execution ports are bottlenecking throughput, etc. of a block of assembly.

Workflow tip for benchmarking: put timing/profiling code in one header file and then different implementations of algorithm in seperate c files so that you only recompile what you need. Also use compile time arguments for different parameters

Getting accurate results

never use sequential input paramaters, use random ones (based on suitable distribution) or branches can start being predictable

when running queries repetedly, you end up measuring throughput, not latency. Fix this by ensuring each query input is dependent on prev iterations (e.g. by passing bitwise or of previous result and next result)

 Another source of bias is the _cold cache effect_, when memory reads initially take longer time because the required data is not in cache yet. Solved with warm-up run.

volatile checksum ensures loop iterations don't interleave 

Layout can have a +- 40% effect on performance which can literally be changed by working directory, one singular malloc, upgrading libc,

stabalizer tool eliminates the effect of layout by randomizing layout, then we use null hypothesis testing to find p value of difference between implementations

normal profilers suck at telling you what to optimize because things are so parallelized and wierdly pipelined that sometimes optimizing a section doesn't help the program. Causal profiling essentially shows you how much of a program speedup would result if you magically sped up a section of your program. magical speed up comes from measuring relative speed and slowing everythign else down.
