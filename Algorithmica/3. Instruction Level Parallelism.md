Each individual instruction can take up to 15-20 cycles. Fetch, decode, execute, and writing back to registers/accessing memory is all pipelined for superscalarness (more than one instruction per cycle even)

Modern CPUs process some instructions *out-of-order* by buffering instructions and executing logically independent ones. Outside scope of book

Pipeline hazards:
- A _structural hazard_ happens when two or more instructions need the same part of CPU (e.g., an execution unit).
- A _data hazard_ happens when you have to wait for an operand to be computed from some previous step. 
- A _control hazard_ happens when a CPU can’t tell which instructions it needs to execute next. Requires complete pipeline flush usually (15-20 cycles)

Branch prediction patterns can be recognized well. A 1000-step repeating pattern can be memorized  

Generally the way the pipeline works is that instructions are fetched, decoder figures out what the instructions are and boundaries, RAT maps the architectural names to physical registers (hundreds of them). Scheduler figures out how to execute these out-of-order by tracking which instruction has its prereqs ready. Results are stored temp. At the end, instruction is retired in order (made permenant in order, with the correct sequence tracked by ROB)  

There are hundreds of physical registers but only a handful of architechural ones because instructions would need to be very long to encode so many addresses and also because it wouldn't even be better. In loops, you would't be able to dynamically allocate to different registers every loop. 

Predication is when we program branchlessly (e.g. `if x>50 then s+=x` becomes `s+=x*(x>50)`) replacing a control hazard with data hazard. Pipeline does not need full flush for mispredict but we are kind of computing both branches. Usually breaks even at abt 75% mispredict rate.

Binsearch can be like 4x faster than `std::lower_bound` because of predication
